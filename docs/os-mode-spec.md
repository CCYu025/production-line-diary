## 0. 目標與範圍

**目標**：在現有網頁介面之外，加一個**可選用（opt-in）的第三種體驗模式**「PLD/OS 1995」。
使用者坐在一間向量線框的 3D 控制室裡，牆上一排 CRT 螢幕各是一個功能；選一台螢幕，鏡頭推進螢幕、轉台雜訊後進入功能；離開時 CRT 關機、鏡頭拉回控制室。

**定位**：給使用者自己與展示用的「炫技模式」。現場日常記錄仍以網頁模式為主。

**範圍內**

- 新的模式入口、3D 控制室（主畫面）、進出轉場、功能畫面的 CRT 外框、合成音效。
- 功能畫面**沿用現有頁面元件**（儀表板、紀錄、新增／編輯、日曆、報表、回收桶、設定），功能、資料、文字完全不變。

**範圍外（明確不做）**

- 手機與平板（寬度 < 1024px 不支援，見 §7）。
- 後端、API、資料格式的任何改動。
- 把功能畫面本身改成 3D（表單、列表在 3D 裡難用，功能畫面一律是 2D 網頁）。
- 網頁模式（標準主題、Cyber 主題）的任何視覺或行為改變。

### 0.1 名詞

| 名詞 | 意思 |
|---|---|
| OS 模式 | 本文件描述的體驗模式。程式代號 `os` |
| 網頁模式 | 現有介面（標準主題或 Cyber 主題） |
| 控制室（Hub） | OS 模式的主畫面：3D 場景＋HUD |
| 頻道（Channel） | 一個功能入口，對應一台 CRT 螢幕，編號 CH-01～CH-07 |
| 工作站（Station） | 進入頻道後的功能畫面：現有頁面元件＋CRT 外框 |
| 轉場（Transition） | 控制室與工作站之間的進出動畫 |
| 導演（Director） | 管理「開機→控制室→進入→工作站→離開」狀態的狀態機 |

## 2. 不可破壞的紅線

1. **網頁模式零差異**：標準主題與 Cyber 主題的畫面、行為、測試結果與 OS 模式導入前完全相同（驗收 S1）。
2. **功能零差異**：工作站裡的每個功能，資料、驗證、文字、流程都和網頁模式相同；OS 模式只包外框與轉場，不改頁面元件的邏輯。
3. **轉場絕不擋住操作**（P3 FX-02 的教訓）：
   - 交接點之前，任何按鍵或點擊都**立刻跳到轉場終點**，不會被吞掉（§5.1）。
   - 交接點之後，目的地畫面立刻可以操作，第一次點擊就要命中目標。
   - **禁止用 View Transitions 做進出轉場**（VT 期間真實 DOM 不可 hit-test）。轉場一律畫在「不接收點擊」的疊層上（§3.4）。
4. **不繞過既有的離開確認**：表單有未儲存變更時，離開工作站必須先經過現有 `useBlocker` 的確認對話框；使用者取消就不播離開轉場。
5. **列印與報表不變**：OS 模式下列印，畫面必須和標準淺色主題列印完全相同；3D、HUD、CRT 外框、疊層一律不印。
6. **沿用 `docs/cyber-theme-spec.md` §2 全部紅線**（對比、嚴重度色與狀態形狀、焦點、字型自行託管、toast 走 `lib/feedback.ts`、不寫死色碼）。3D 場景的線條顏色從 Cyber token 讀取，不另寫色碼。
7. **無障礙**：3D 場景只是裝飾，所有操作都能透過 HUD 的真實按鈕與鍵盤完成；螢幕閱讀器讀得到每個頻道的名稱與即時訊號（§6）。
8. **`prefers-reduced-motion: reduce` 一律生效**：不播鏡頭移動與轉場動畫，改成直接切換（§5.5）。
9. **相依套件鎖定精確版本**，新增套件只限 §3.6 列出的；要加其他套件先問設計師。
10. **資料安全**：同 `refactor-plan.md` §5，真實資料夾禁止讀寫、禁止當 `DATA_DIR`；開發與驗證一律用複製的範例資料、非 3000 的 port、`NO_OPEN_BROWSER=1`。

## 3. 架構

### 3.1 三層分離

```
┌ 控制室（Hub） ─────────┐   ┌ 轉場（Transition） ┐   ┌ 工作站（Station） ─┐
│ 3D 場景（可替換外觀）  │ → │ 疊層動畫，可跳過   │ → │ 現有頁面＋CRT 外框 │
│ HUD（真實按鈕）        │ ← │                    │ ← │                    │
└────────────────────────┘   └────────────────────┘   └────────────────────┘
                 導演（Director 狀態機）統一管理三層
```

- 三層之間**只透過導演溝通**，彼此不直接呼叫。
- 之後要換主畫面（例如網路空間、低多邊形地球）時，只換控制室這一層。

### 3.2 模式啟用與路由

**路由與網頁模式共用，依模式切換外殼**（不加 `/os/ch/...` 之類的前綴）。
理由：現有頁面有十多處以絕對路徑導航（表單存檔後到 `/dashboard` 或 `/records?open=…`、詳情面板的編輯與複製、`lib/drill.ts` 的圖表點進列表、toast 的「查看」、各處的 `<Link to="/records/new">`）。加前綴會讓這些導航掉回網頁模式，而紅線 2 不允許為此改頁面元件。

- 根路由的外殼依模式決定：網頁模式是現有 `AppShell`，OS 模式是 `OsShell`。`OsShell` **整個延遲載入**（`React.lazy`），網頁模式不下載任何 3D 程式碼。
- **控制室**是新路由 `/os`。只在 OS 模式存在；網頁模式開 `/os` 導向 `/dashboard`。
- **工作站**就是現有路由（`/dashboard`、`/records`、`/records/63/edit`…），在 OS 模式下由 `OsShell` 包上 CRT 外框。
- **頻道由路徑推導**，對照表集中在 `features/os/channels.ts`（唯一真相）：

  | 路徑 | 頻道 |
  |---|---|
  | `/dashboard` | CH-01 |
  | `/records`、`/records/:id/edit` | CH-02 |
  | `/records/new`（含 `?copy=`） | CH-03 |
  | `/calendar` | CH-04 |
  | `/report` | CH-05 |
  | `/trash` | CH-06 |
  | `/settings` | CH-07 |

- 模式狀態：`web/src/lib/mode.ts`，`getModePreference()`／`setModePreference()`，key `pld.mode`，每次讀寫都包 try/catch，失敗回傳 `web`。`?mode=os`／`?mode=web` 可覆寫並寫回，套用後從網址移除（比照 `?theme=`）。
- `OsShell` 掛載時在 `<html>` 設 `data-mode="os"`，卸載時移除；`os.css` 的規則都以它開頭。網頁模式的 `<html>` 沒有這個屬性。
- `/` 依模式導向：網頁模式 `/dashboard`，OS 模式 `/os`。
- **瀏覽器上一頁／下一頁**：路由是唯一真相，導演依「前後兩個路徑的頻道」決定播哪種轉場（§3.3）。
- **離開 OS 模式**（D5）：留在目前的路徑，只把外殼換回 `AppShell`；在控制室離開時導向 `/dashboard`。

### 3.3 導演狀態機

| 狀態 | 意思 | 允許的輸入 |
|---|---|---|
| `BOOT` | 開機序列 | 任意鍵或點擊：跳過開機 |
| `HUB` | 控制室待機 | 選頻道、進入、指令列、離開 OS 模式 |
| `ENTERING(ch)` | 進入轉場（控制室 → 工作站） | 交接點前：任意輸入跳到 `STATION`；交接點後：輸入交給工作站 |
| `STATION(ch)` | 工作站 | 頁面本身的一切操作；Esc（§5.4 的條件）、◀ HUB、上一頁回到 `/os`：離開 |
| `SWITCHING(from, to)` | 工作站之間切換（短轉場） | 同 `ENTERING` |
| `EXITING(ch)` | 離開轉場（工作站 → 控制室） | 交接點前：任意輸入跳到 `HUB`；交接點後：輸入交給 HUD |

**路由變化如何對應到轉場**（導演只看前後兩個路徑的頻道）：

| 從 → 到 | 轉場 |
|---|---|
| `/os` → 某頻道 | `ENTERING`（完整進入，§5.2） |
| 某頻道 → `/os` | `EXITING`（完整離開，§5.3） |
| 頻道 A → 頻道 B（例如表單存檔後到儀表板、圖表點進列表、toast「查看」、指令列切換） | `SWITCHING`（短轉場，§5.4） |
| 同一頻道內（例如 `/records` → `/records/63/edit`、`?open=` 參數變化） | 不播轉場 |

- 狀態機是純函式（`reducer`），放在 `web/src/features/os/director/`，**必須有完整單元測試**，涵蓋每個狀態的每種輸入與上表每種路由變化。
- 轉場進行中又發生路由變化（例如連按上一頁）：目前的轉場直接跳到終點，再依新的路由變化決定下一段轉場。
- 路由在轉場**一開始**就切換，頁面立刻開始載入資料；轉場只是視覺，不延後任何 API 呼叫。
- `STATION` 時控制室的 3D 繪製迴圈**完全停止**（不是只隱藏），省 GPU。

### 3.4 疊層（轉場的繪製方式）

- 進出轉場畫在一個全螢幕 `<canvas>` 疊層上：`pointer-events: none`、`aria-hidden="true"`。
- **不擷取網頁畫面**：進入時，鏡頭推進的那台螢幕上顯示的是「頻道台標卡」（例如 `CH-02 RECORDS`），不是網頁內容。台標卡填滿畫面的瞬間，在雜訊遮蔽下換成真實工作站。離開時反過來。
- 轉場的「跳過」只是把疊層動畫直接設到終點，不影響下面網頁的狀態。

## 4. 視覺語言

### 4.1 向量線框規則

- **只有線、沒有面**：所有 3D 物件只畫邊線，不畫貼圖、不打光、沒有陰影。
- **色彩取自 Cyber token**：

  | 用途 | token |
  |---|---|
  | 一般線條 | `--line-strong`（遠處淡入 `--line`） |
  | 選中物件、四角框 | `--accent` |
  | 雷達光點 | 嚴重度色（`--good`、`--warning`、`--serious`、`--critical`），和列表左側色條一致 |
  | 背景與霧 | `--page` |

  3D 場景在初始化時以 `getComputedStyle` 讀 token，**不寫死色碼**。
- **景深**：遠處線條以線性霧淡入背景色，避免畫面雜亂。
- **線條數量上限**：整個控制室場景線段總數 ≤ 4,000（驗收 P1 的效能前提）。
- **線寬**：WebGL 的線寬固定 1 像素（瀏覽器忽略 `linewidth`）。在 640×360 繪製、放大約 3 倍後約 3px 粗，這正是想要的向量顯示器效果。選中四角框等需要更粗的線，用 `three/examples/jsm/lines` 的 `Line2`。

### 4.2 年代感處理

以下效果只用在 §4.7 的 A 區（3D 場景與轉場），全部在 WebGL 裡完成，不處理網頁元素。

| 效果 | 做法 | 預設 |
|---|---|---|
| 低解析度 | 3D 以內部解析度 640×360（CRT 強度「濃」時 426×240）繪製到離屏緩衝，最近鄰放大 | 開 |
| CRT 著色器 | 放大時經過一道自製片段著色器，依序做：桶狀弧面 → 色偏 → 掃描線 → 映像管紋理 → 螢光暈開 → 暗角 → 閃爍（細節見 §4.7） | 開 |
| 磷光殘影 | 前一幀以 85% 不透明度疊回（自製回饋緩衝，不用後處理套件） | 開；效能不足時自動關（§9.4） |
| 輕微晃動 | 控制室鏡頭以極小幅度呼吸式晃動（±0.3°，週期 8 秒） | 開；減少動態效果時關 |

網頁層（HUD、工作站）沿用 Cyber 主題的 `body::after` 靜態掃描線，B 區另加淡紋理（§4.7）。

### 4.3 控制室場景

- **地板**：透視網格，延伸到霧中。
- **螢幕牆**：7 台 CRT 以弧形排列在鏡頭前方，每台是一個線框外殼加一個螢幕面。
- **螢幕面的內容**：用 2D Canvas 畫成貼圖，內容是頻道代號、名稱、一個即時訊號（§4.4）。這是唯一允許的「貼圖」，因為它本身就是一塊會發光的螢幕。
- **選中提示**：被選中的螢幕外框變主青色，外圍加四角框（分鏡第 1 格）。
- **雷達台**：螢幕牆前方地面上的圓形線框台，掃描線旋轉；每台機台是一個光點（§4.4）。
- **待機巡視**：60 秒無操作時，鏡頭緩慢巡視整間控制室；任何輸入立刻回到原位。

### 4.4 即時訊號（主畫面要有用）

全部用**現有 API**（`getMeta`、`listRecords`、`getAggregate`）與現有的 TanStack Query 快取，不新增後端端點。

| 頻道 | 螢幕上的訊號 |
|---|---|
| CH-01 儀表板 | 待處理件數 |
| CH-02 紀錄 | 今日新增筆數 |
| CH-03 新增 | 閃爍的 `READY▮` |
| CH-04 日曆 | 今天日期與當日筆數 |
| CH-05 報表 | 本月筆數 |
| CH-06 回收桶 | 回收桶筆數 |
| CH-07 設定 | 機台數 |

- **雷達光點**：近 7 天有紀錄的機台各一個點，顏色取該機台最嚴重的未解決紀錄。
- **資料更新**：現有查詢設定沒有定時更新（`staleTime` 10 秒）。只在 `HUB` 狀態時，每 30 秒重新抓一次紀錄（沿用現有 `listRecords` 與查詢快取，不新增端點）；離開 `HUB` 就停止。
- **新異常**：進入 `HUB` 之後才出現的紀錄（id 大於進入時看到的最大 id）。新異常的光點會持續閃爍、雷達外圈緩慢呼吸，直到使用者確認（見 X2 備註）；提示音在 X4；第一次載入不算新異常。
- 光點的角度依機台名稱的雜湊固定，每次開啟位置相同。

### 4.5 HUD

HUD 是疊在 3D 場景上的一般網頁層，是 OS 模式的**真實操作介面**，3D 場景只是它的視覺化。

- **頻道清單**（畫面底部）：7 個真實的 `<button>`，文字例如 `CH-02 紀錄 · 今日 3`。方向鍵移動、Enter 進入；和 3D 螢幕的選中狀態雙向同步。
- **狀態列**（畫面頂部）：`PLD/OS 1995`、時間、音效狀態、`EXIT TO WEB` 按鈕。
- **指令列**：控制室按 `/`、任何地方按 `Ctrl+K` 開啟（快速鍵規則見 §5.4），可輸入 `dash`、`rec`、`new`、`cal`、`rep`、`trash`、`set`、`rec 63`（直接開某筆紀錄）、`exit`、`help`；輸入有自動完成。
- 字型、色彩、焦點環全部沿用 Cyber 主題。

### 4.6 工作站

- 頁面元件外面包一個 **CRT 外框**：圓角螢幕邊框、四角輕微暗角、右上角頻道台標（例如 `CH-02`）。
- 外框內就是現有的 Cyber 主題頁面，在外框內捲動。
- **浮層蓋在一切之上**：現有的對話框、詳情面板、彈出選單、燈箱、toast 都掛在 `<body>` 下，會蓋住整個畫面（包含外框與 HUD），這是預期行為，與 §4.7 的疊放順序一致；不得為了把它們關進外框而改元件。
- 外框左上角有一個真實的「◀ HUB」按鈕，等同 Esc。
- 網頁模式的側欄與手機底部列**不顯示**；頁面之間的切換回控制室、用指令列，或頁面本身的連結（播短轉場，§3.3）。

**`OsShell` 必須繼承 `AppShell` 的行為**（逐項比照 `web/src/app/AppShell.tsx`）：

1. 換頁後焦點移到主內容（`<main id="main">`，第一次載入不搶焦點）。
2. `document.title` 依路由的 `handle` 設定（`○○｜產線日誌`）。
3. 「跳到主要內容」連結。
4. 列印時的版面處理（`print:` 類別：外殼不佔版面、主內容無邊距）。
5. 頁面標題列沿用現有的標題元件（含 Cyber 的標題打字效果），放在 B 區標題列。

**主題**（D6）：進入 OS 模式時以「只套用、不寫入」的方式把 `<html data-theme>` 設成 `cyber`：
- **不得**呼叫 `switchTheme()`：它會改寫 `pld.theme` 偏好，還會播 FX-38 主題切換掃描。
- 離開 OS 模式時，依 `pld.theme` 重新套用原本的主題。
- Cyber P3 的開機畫面（`BootScreen`，FX-01）在 OS 模式**不播放**，以免和 OS 開機（§5.5）重複。

### 4.7 CRT 強度區

CRT 的解析度與映像管顆粒感只用在裝飾性的部分；資料與圖片一律清晰。比喻是：控制室是「映像管裡的畫面」，工作站的資料是「訊號鎖定後的清晰畫面」，進入轉場的 E4「訊號鎖定」就是從 A 區變到 C 區的那一刻。

| 區 | 範圍 | CRT 處理 |
|---|---|---|
| **A 完整 CRT** | 3D 控制室、開機序列、進出轉場的疊層、頻道台標卡、雷達台 | §4.2 全部效果 |
| **B 輕度 CRT** | HUD 外框、狀態列、工作站的 CRT 外框、頁面標題列 | 原生解析度；只疊淡掃描線與淡映像管紋理；文字保持銳利 |
| **C 不做 CRT** | 工作站內容：紀錄文字、數字、表格、表單、圖表、照片、燈箱、報表與列印 | 完全清晰，與網頁模式 Cyber 主題相同（只有既有的 `body::after` 靜態掃描線） |

**A 區著色器細節**

| 效果 | 規格 |
|---|---|
| 桶狀弧面 | 畫面向外凸，邊緣最大位移約 3%；弧面外的區域填背景色 |
| 色偏 | 紅、藍通道往相反方向錯開 ≤ 0.7 個低解析度像素 |
| 掃描線 | 每列低解析度像素之間有暗縫；暗縫寬度隨亮度變窄（亮線看起來更粗更亮） |
| 映像管紋理 | Trinitron 式紅綠藍細直條（不用點狀遮罩：90 年代電腦螢幕常見，且在液晶上較不易摩爾紋） |
| 螢光暈開 | 亮線周圍的柔和光暈，以低解析度緩衝做兩次模糊後疊加 |
| 暗角 | 四角變暗約 25% |
| 閃爍 | 全畫面亮度以 ±1.5% 不規則跳動；減少動態效果時關 |

**C 區不做 CRT 的理由**：要把網頁變低解析度或弧面變形，只能先把網頁畫成圖片再處理，這樣網頁就不能點、不能選字、不能輸入，螢幕閱讀器也讀不到，違反紅線 3 與 7；用 CSS 模糊或縮放假裝低解析度，資料難讀，大面積濾鏡也很吃效能（Cyber P2–P4 量測過）。

**疊放順序**（由下到上）：3D 畫布（A）→ 工作站頁面（C）→ B 區外框與淡紋理 → 轉場疊層（A）→ 照片燈箱、對話框、toast。
B 區的紋理與掃描線只能蓋在 HUD 與外框範圍內，**不得蓋到工作站的內容區**；燈箱、對話框、toast 一律在所有 CRT 疊層之上。

**摩爾紋**：B 區的映像管紋理用 CSS 疊層畫時，條紋週期必須以實際螢幕像素計算（依 `devicePixelRatio` 換算成整數裝置像素），不得用固定 CSS 像素，否則 Windows 125%／150% 顯示縮放下會出現摩爾紋。A 區在著色器內同樣以裝置像素計算。

**CRT 強度設定**（D7）

| 設定 | A 區 | B 區 | C 區 |
|---|---|---|---|
| 關 | 只有 640×360 低解析度，不做著色器效果 | 無 | 清晰 |
| 標準（預設） | 640×360＋全部效果 | 淡紋理＋淡掃描線 | 清晰 |
| 濃 | 426×240＋效果加強（暈開、暗角、弧面各約 1.5 倍） | 紋理加深 | 清晰 |

## 5. 轉場與動畫

### 5.1 共通規則

1. **交接點規則**（每段轉場都標出交接點，見 §5.2–5.4）：
   - **交接點之前**：目的地還沒出現。第一次按鍵或點擊＝跳到終點，這次輸入**不會**傳給下面的畫面（避免盲點到還看不見的按鈕）；做法是轉場期間在 capture 階段攔截一次。
   - **交接點之後**：目的地已經出現，攔截立刻解除，輸入直接交給目的地；剩下的雜訊淡出只是視覺，不跳過也不攔截。
2. **轉場不延後任何事**：路由切換、API 呼叫在轉場一開始就發生；焦點在交接點移到目的地（工作站的主內容或控制室的頻道按鈕）。轉場只是視覺。
3. **只用疊層 canvas 與 3D 鏡頭**做轉場，不用 View Transitions、不對網頁元素做 `clip-path` 進場動畫。
4. 所有時間定義成 token，放在 `features/os/transition/timing.ts`，測試會檢查總長上限。
5. 3D 與疊層動畫只能在 `requestAnimationFrame` 裡更新，不得造成網頁版面重排（CLS = 0）。

### 5.2 進入轉場（控制室 → 工作站）

| 段落 | 時間 | 畫面 | 聲音 |
|---|---|---|---|
| E1 鏡頭推進 | 0–600ms | 鏡頭朝選中的螢幕推進，其他螢幕滑出畫面 | 推進時的低頻上升音 |
| E2 台標卡 | 600–750ms | 螢幕面填滿畫面，顯示 `CH-02 RECORDS`、`signal lock ▮▮▮▯` | 繼電器喀噠一聲 |
| E3 轉台雜訊 | 750–1000ms | 疊層出現雜訊、水平撕裂、垂直滾動；雜訊遮蔽下 3D 隱藏、工作站現身 | 轉台雜訊聲 |
| E4 訊號鎖定 | 1000–1200ms | 雜訊淡出，工作站完整顯示，台標縮到右上角 | — |

總長 ≤ 1,200ms。**交接點：875ms**（E3 中段，雜訊遮蔽下工作站現身）；焦點在交接點移到頁面主內容（沿用現有換頁的焦點規則）。

### 5.3 離開轉場（工作站 → 控制室）

| 段落 | 時間 | 畫面 | 聲音 |
|---|---|---|---|
| X1 垂直收合 | 0–150ms | 工作站畫面（疊層模擬）垂直壓扁成一條亮線 | CRT 關機的高頻「啾」 |
| X2 收成亮點 | 150–300ms | 亮線水平收成一個亮點 | — |
| X3 亮點殘留 | 300–400ms | 亮點淡出 | — |
| X4 鏡頭拉回 | 300–900ms（與 X3 重疊） | 從那台螢幕拉回控制室原位 | 低頻下降音 |

- 總長 ≤ 900ms。
- **交接點：300ms**（亮點出現、控制室與 HUD 開始顯示）；焦點在交接點回到對應頻道的 HUD 按鈕。
- X1 的「工作站畫面」用簡化的亮面塊模擬，**不擷取網頁**。

### 5.4 短轉場與快速鍵

**短轉場**（`SWITCHING`，工作站之間切換）：只有 E3＋E4 的縮短版，雜訊 150ms＋訊號鎖定 150ms，總長 ≤ 300ms；**交接點：75ms**。

**快速鍵**（符合 WCAG 2.1.4：單一字元快速鍵只在控制室有效，工作站內只用含修飾鍵的組合）：

| 按鍵 | 在哪裡有效 | 作用 |
|---|---|---|
| ← → | 控制室 | 選頻道 |
| Enter | 控制室 | 進入選中的頻道 |
| 1–7 | 控制室 | 直接進入對應頻道 |
| `N` | 控制室 | 直接進入 CH-03 新增（完整進入轉場） |
| `/` | 控制室 | 開指令列 |
| `M` | 控制室 | 靜音切換（工作站內用狀態列按鈕） |
| `Ctrl+K` | 任何地方 | 開指令列（工作站內要新增紀錄就輸入 `new`，播短轉場） |
| Esc | 工作站 | 離開回控制室（條件見下） |

- 所有快速鍵在焦點位於輸入框、文字區、下拉選單、可編輯內容時**不作用**（`Ctrl+K` 除外）。
- **Esc 的條件**：只有在**按下的那一刻**（capture 階段記錄）沒有任何對話框、面板、彈出選單、燈箱開著，而且焦點不在輸入元件上，Esc 才算「離開工作站」。這樣一次 Esc 只會關掉浮層，不會連工作站一起離開。

### 5.5 開機序列

| 段落 | 內容 |
|---|---|
| B1 | 黑畫面，`PRESS ANY KEY`（點擊也可） |
| B2 | BIOS 自檢文字逐行出現：記憶體、`PLD/OS 1995`、機台數、紀錄數（真實數字） |
| B3 | CRT 亮起（一條亮線展開成全畫面） |
| B4 | 控制室線框從中心向外描繪出現 |

- 完整版 ≤ 4 秒，每個分頁工作階段只播一次（D3）；之後是只有 B3＋B4 的短開機，≤ 1 秒。
- 任意鍵跳過。
- **B1 的第一次按鍵用來啟用音效**（瀏覽器要求互動後才能出聲）。
- **短開機沒有 B1**，所以重新整理或新開頁面時，聲音要等使用者**第一次按鍵或點擊**才會出現；狀態列的音效圖示在這之前顯示「待啟用」，避免誤以為音效壞了。

### 5.6 減少動態效果

開啟 `prefers-reduced-motion: reduce` 時：

- 不播開機 B2–B4，直接顯示控制室（B1 保留，用來啟用音效）。
- 進出轉場改成**直接切換**，不播任何疊層動畫與鏡頭移動。
- 控制室鏡頭固定、不巡視、不晃動；雷達掃描線停止，光點常亮（依分級上色）、不脈衝、不閃爍。
- 音效照常（音效與動態效果無關）。

## 6. 無障礙

1. **完全可用鍵盤操作**：控制室透過 HUD 按鈕，工作站沿用現有頁面的鍵盤操作。
2. **3D 畫布**是 `aria-hidden="true"`，所有資訊都在 HUD 的文字裡。
3. **頻道按鈕的可及名稱**包含訊號，例如「CH-02 紀錄，今日 3 筆」。
4. **焦點**：進入工作站時，焦點移到頁面主內容；離開時，焦點回到該頻道按鈕。
5. **狀態宣告**：轉場開始與完成，用一個 `aria-live="polite"` 區域宣告「進入紀錄」／「回到控制室」。
6. **開機文字**是裝飾（`aria-hidden`），另有一句螢幕閱讀器可讀的「PLD/OS 載入中」。
7. **對比**：HUD 文字對比 ≥ 4.5:1（沿用 Cyber 色票，測試同樣檢查）。

## 8. 音效

- **全部用 Web Audio 即時合成**：振盪器＋雜訊緩衝＋包絡，不使用任何音檔。
- 音效表放在 `features/os/audio/sounds.ts`，每個音效是一個參數物件，有單元測試檢查參數範圍。

| 事件 | 聲音 | 長度 |
|---|---|---|
| 開機 B2 | 撥接連線音（雙音頻＋雜訊）、BIOS 嗶一聲 | ≤ 2.5s |
| 控制室待機 | CRT 低頻嗡聲，非常小聲，持續 | 持續 |
| 選頻道（左右移動） | 繼電器喀噠 | ≤ 60ms |
| 進入 E1／E3 | 上升音、轉台雜訊 | 對應段落 |
| 離開 X1／X4 | 高頻「啾」、下降音 | 對應段落 |
| 雷達新異常 | 短促雙音提示 | ≤ 200ms |
| 指令錯誤 | 低音嗶 | ≤ 150ms |

- **主音量上限**：-18 dBFS，所有音效經過同一個總音量節點。
- **靜音**：`M` 鍵或狀態列按鈕；偏好存在 `pld.os.sound`（`on`／`off`），預設 `on`。
- `AudioContext` 建立失敗時一律靜默，不影響任何功能。
- 分頁切到背景時暫停待機嗡聲。

  - **待機巡視**：`HUB` 無輸入 60 秒開始；任何按鍵、點擊、滾輪、觸控立刻結束，且輸入不被吞掉；其他狀態不巡視；減少動態效果不巡視。選取時鏡頭轉向選中螢幕 ≤ 3°（只轉角度、不位移）、約 250ms 內到位，不擋輸入；進入推近與離開拉遠的目標是**選中的螢幕**。
  - **CRT 強度（D7）**：`localStorage` 的 `pld.os.crt`（`off`｜`std`｜`max`，預設 `std`，讀寫皆 try/catch）；狀態列三段切換（真實按鈕、`aria-pressed`）與指令列 `crt off|std|max`（含 help 與 Tab 補全；`crt` 不帶參數＝顯示目前強度）。A 區：關＝640×360 只有低解析度、不做著色器效果；標準＝目前；濃＝426×240、暈開／暗角／弧面各 1.5 倍；切換不得洩漏 render target。B 區：只蓋在 HUD 外框與工作站 CRT 外框，不蓋 `<main>`；條紋週期以整數裝置像素由 `devicePixelRatio` 計算（3 的倍數，dpr 改變時重算），`pointer-events: none`，疊放在燈箱、對話框、toast 之下；C 區任何強度都清晰。
  - **3D 螢幕上的字**：不放小的中文（場景只渲染在 640×360／426×240，小字讀不出來；中文名稱在 HUD 按鈕）。每台螢幕：上方頻道代號（粗體、大）、中央大字、下方短的英文大寫標籤——CH-01 `PENDING`、CH-02 `TODAY`、CH-03 `READY`（沒有標籤）、CH-04 大字 `MM/DD`＋標籤 `TODAY`＋當日筆數小字、CH-05 `MONTH`、CH-06 `TRASH`、CH-07 `UNITS`；不顯示英文頻道名稱（太小讀不出來）。字型取 IBM Plex Mono 600（已載入的最粗字重）、加 --page 色外描邊，頻道代號與標籤盡量佔滿螢幕寬度；螢幕貼圖用 mipmap＋非等向過濾縮小（濃的 426×240 下一台螢幕只有 30–40 像素寬）。
  - **開機 B3 的樣子**：只有「線」是亮的——一條細亮線由中心向兩側展開到整個寬度，再垂直打開成暗的光柵（亮度 ≤ 亮線峰值的 20%，不是整個畫面閃白）；B4 開始時光柵與殘餘的亮線逐漸淡出，同時線框由中心向外描繪，兩者直接交疊、中間沒有黑畫面。完整開機計時 3,900ms（量到控制室現身約 3,905–3,915ms）、短開機計時 980ms（量到控制室現身約 980–992ms，上限 1,000ms）；開機結束那一刻不做重活：中文字型子集在開機 B2 期間（一掛載後 100ms）就開始載入，控制室內容（螢幕、雷達、HUD）早已在底下建好，現身時不建立任何東西。
  - **HUD 窄版標籤**：頻道按鈕從 1024px 起維持一行；視窗 < 1440px 時可見文字改為精簡的 `CH-02 紀錄 3`（沒有「· 今日」）、內距更緊，accessible name 永遠是完整的 `CH-02 紀錄 · 今日 3`。雷達光點：全部已解決的光點用 `--ink-muted`（安靜的文字色）往 `--page` 混 70%，亮度約為嚴重度色的 2/3（設計裁示的 35–45% 在 CRT 掃描線與暗角下的 1px 細線實測太暗，看不見，所以以「清楚看得見」優先），在深色背景上清楚看得見（取代先前的 `--line-strong`：細線在 CRT 效果下實測看不見）；顏色一律經 `readOsColors` 讀 token，不寫死，角度與半徑各用獨立的雜湊（FNV-1a ＋ murmur3 fmix32，不同種子）。
  - **場景實作備註**：構圖：1920×1080 時整面牆占寬度約 76–78%、中間螢幕面中心在畫面高度約 45%（鏡頭高度 7、微微俯視，畫面上方不留大片空白，地板格線與雷達台在牆下方）；弧半徑 10.5、±55°，外殼縮窄，使相鄰外殼投影後的水平間距 ≥ 視窗寬度的 1%（整面牆的實際高度約占畫面 25%；與「間距 ≥ 1%」「牆寬 ≥ 75%」同時成立時無法更高，取間距優先）；選取偏航 ≤ 3° 且不位移，選 CH-01／CH-07 時整面牆仍在視窗內、兩側邊距 ≥ 4%（以純函式投影在 1920×1080、1280×720、1024×640 驗證）；螢幕亮度（選中 100%／未選中 60%）用材質顏色控制，選取不重畫貼圖；選中螢幕的四角框是 Line2（`LineSegments2`，8 段）；光點與脈衝環的線段以預先配置的上限計入 4,000 段預算；點選射線在 CRT「標準／濃」時先反算桶狀弧面的位移，所以點到的是畫面上看到的那台；開機的 BIOS 文字畫進場景緩衝（經過 CRT 管線），B3 亮線與 B4 揭曉是 CRT 著色器的 uniform，控制室在底下已經就緒，所以沒有「開機後閃一下」。巡視輸入後 150ms 內收回（不是瞬移）。

**X3 狀態與實作備註**

- 狀態：**實作中，合併前**。第 1 部分（磷光殘影、裝置門檻）設計師決策：
  - **磷光回饋（A 區）**：自製乒乓緩衝（`CrtPipeline` 內的 `accA`／`accB`，與場景緩衝同尺寸、最近鄰），著色器 `PHOSPHOR_FRAG` 逐通道取「本幀場景」與「上一幀合成結果離 `--page` 的差 × keep」中離背景較遠的那一個（與背景明暗無關；靜止的線不會變亮）；CRT pass 與暈開都讀合成結果。殘留比例關＝不做、標準 0.85、濃 0.88，每 16.67ms 幀；依實際 dt 換算 `keep^(dt/16.67ms)`，dt 夾在 [1, 100]ms。8 位元緩衝每幀多扣 1.5/255，殘影最後收斂回 `--page`，不會卡出永久鬼影。
  - **不拖影的情況**：第一幀、dt > 250ms（暫停或分頁隱藏後）、緩衝縮放後、開機（`setBoot`／BIOS 文字貼圖）期間與開機剛結束的那一幀——一律 keep＝0（只取場景）。所以開機 B3／B4 的樣子不變。
  - **不建回饋緩衝**：CRT 強度「關」、減少動態效果、本分頁已被自動降級。強度切換時整條管線重建，`dispose` 同時釋放回饋緩衝；`?osdebug=gldebug` 的 `__osGl()` 多了 `phosphor`（回饋緩衝是否存在）與 `renderTargets`（存活的離屏 render target 數，強度來回切換不得增長）。
  - **自動降級（P1 降級順序第一步）**：`PhosphorGovernor`（純邏輯）以滾動視窗累積 3 秒的幀時間，中位數 fps < 50 就降級；單次尖峰不影響；暫停（dt > 250ms）、離開 `HUB`、開機中、文件隱藏都清空視窗重新累積。降級＝模組層級記憶體旗標（不持久化）＋一行 `console.info`，管線重建且不再建回饋緩衝；整個分頁生命週期內維持。
  - **2D 轉場疊層拖尾**：`transition/trail.ts` 的 `trailCoverAlpha`／`applyTrail`——每幀以 `--page` 色蓋 `1 − keep^(dt/16.67ms)`（不整個清掉）；CRT 關或第一幀＝全清。注意拖尾是向 `--page` 色衰減而不是向透明，疊層上若要「拖尾後露出下層」，要在拖尾亮點不再需要時整個清掉（由第 2 部分的轉場視覺決定接線方式）。
  - **裝置門檻畫面**：終端機視窗（等寬字、`--accent` 邊框、標題列 `PLD/OS 1995 — TERMINAL`、閃爍游標 ▮，週期約 1 秒、`steps(1)`）；`prefers-reduced-motion: reduce` 時游標常亮不閃；「改用網頁模式」按鈕行為與 `data-os` 屬性不變。樣式只在 `os.css`，列印時照舊隱藏。
- 第 2 部分（轉場正式版）設計師決策。時間 token 與交接點全部不變（進入 1200／875、離開 900／300、短轉場 300／75）；所有轉場視覺都是「距轉場開始毫秒 t」的純函式（`transition/choreo.ts`、`hub/faceRect.ts`、`hub/slide.ts`），每幀只在既有的 rAF 迴圈裡套用：
  - **E1 鏡頭與兩側螢幕**：鏡頭進度仍是 `cameraProgress`（ease-in-out 三次，600ms 到 1）。推到位的距離 `CLOSE_DISTANCE` 改由 `FACE_FILL_FRAC = 0.84`（螢幕面高度占視窗高度）與垂直視角推出（約 2.16，原本 1.25 會讓螢幕面比視窗大約 45%、卡片出現時才「縮」一下，那就是 X1 的「縮放跳一下」）。另外 6 台沿同一個弧線往遠離選中螢幕的方向滑開 40°，並以 `smoothstep(p: 0.05–0.8)` 把外殼與外框的顏色混向 `--page`（融進霧；不用透明度，所以不會觸發著色器重編譯），螢幕面亮度同步乘上 `(1 − 淡出量)`；進度 p 與鏡頭同一條曲線，離開 X4 倒回去。每台螢幕的外殼材質各自一份。進入／離開期間鏡頭與側邊螢幕鎖定該次轉場的目標螢幕（離開後半段改選頻道不會讓鏡頭跳位置）。
  - **E2 卡片外框接續**：`faceRectAt()` 把選中螢幕面的四個角投影後反算 CRT 桶狀弧面（`c·(1+k|c|²)` 的反函數，與滑鼠拾取同一條公式），取外接矩形＝600ms 那一刻螢幕面的畫面位置；卡片外框以這個矩形為起點，E2 的 150ms 內 ease-out 展開到全幅外框（四周各 24 個疊層像素）。弧面外框的邊是直線、真實螢幕面的邊略彎，差距 < 0.6% 視窗高。卡上的字：頻道代號 `CH-0x` 是大的台標（見下），英文代號（例如 `RECORDS`）與 `signal lock` 列是卡片文字（OSD，不受撕裂與滾動影響）。
  - **signal lock 排程**（進入）：E2 開始 0 格，625／675／725ms 依序亮到 ▮▮▮▯（750ms 前 3 格），E4 開始（1000ms）第 4 格亮（▮▮▮▮）；短轉場：0／25／50ms 亮 3 格（75ms 交接點前已是 ▮▮▮▯），訊號鎖定開始（150ms）第 4 格。格子用矩形畫（不依賴 ▮ 字形），卡片文字在鎖定後淡出（進入 1060–1130ms、短轉場 175–225ms）。
  - **E3 雜訊／撕裂／滾動**：雜訊不透明度 0.55→1（到交接點前 60ms）→0.85（交接點後 20ms）；3–5 條水平撕裂帶（數量與位置由 seed 決定，位移每 33ms 換一次，強度 1→0.4）；一次減速的垂直滾動（`1−(1−k)³`，剛好滾一整圈，接縫對齊）加一條隨滾動減速移動的亮條。交接點之前疊層不透明（卡片＋雜訊，向 `--page` 拖尾）；交接點之後疊層透明，下面是已經現身的工作站，只剩雜訊與撕裂亮痕。**交接點之後的雜訊不拖尾**：拖尾會在工作站上留下鬼影，破壞「最後 60ms 完全乾淨」的排程。
  - **E4 雜訊淡出與乾淨尾段**：不透明度與顆粒強度（雜訊顏色表的對比）從 1000ms 起「一起」線性淡到 0，在 1140ms（總長 − 60ms）達到 0，之後疊層與台標層都已清空、不再繪製。短轉場同理：150ms 起淡出、240ms 為 0（原本的 150–300ms 線性淡出取代為 150–240ms；`switchNoiseAlpha` 的測試隨之調整）。
  - **台標落點與解析度**：頻道小標 `CH-0x` 畫在裝置解析度的獨立畫布 `#os-overlay-tag`（尺寸＝視窗 × min(dpr, 2)，z-index 41，`pointer-events: none`，列印隱藏），不在 640×360 的疊層上：640×360 在 1920 寬時 1 像素＝3 個 CSS 像素，≤ 2px 的落點誤差辦不到、字也會糊。600ms（短轉場 0ms）起在畫面中央（高度 = 視窗高 × 0.085，水平置中、垂直在 40% 處），1000ms 起（短轉場 150ms）ease-out 縮向右上角，1140ms（短轉場 240ms）落地並清空，由下面的真實台標接手。落點終點是交接點對 `[data-os="tag"]`（`StationFrame` 的台標）讀一次的 `getBoundingClientRect()`，矩形各分量線性插值，終點與目標矩形完全相等（誤差 0）；字型 `600 14px IBM Plex Mono`、letter-spacing 0.12em（與 `.os-tag` 一致），基線用字型量測的上升／下降值置中。讀不到元素時用右上角預設位置，不丟錯。不對任何網頁元素做動畫。台標層畫布在控制室閒置時預熱（配置、字型量測、字型載入），點擊那一刻不建任何東西（代價：多一塊視窗大小的畫布記憶體）。
  - **離開 X1–X3**：不透明 `--page` 疊層上畫「亮面塊」（範圍＝工作站外框 `.os-frame` 的內縮矩形，左右 10px、上 8px、下 10px，不擷取網頁）：X1（0–150）垂直壓成 2 像素亮線（ease-in 三次），X2（150–300）水平收成 6×6 亮點（ease-in 三次），顏色由偏 accent 的底色變白熱；CRT 開時每幀以 `applyTrail` 向 `--page` 拖尾（亮線、亮點留下磷光殘影）。交接點（300）疊層清空，之後亮點 X3（300–400）以 `applyAlphaTrail`（destination-out，向透明衰減）拖尾淡出；400ms 起疊層清空不再繪製。離開不畫任何文字。
  - **X1 遺留「signal lock 被 HUD 列切掉」**：從 CSS 推演未能重現——X0 起疊層 z-index 40 就高於 HUD 20，疊層與 `.os-root` 都沒有 overflow／clip／transform。X3 的做法：離開不再畫任何文字；其餘疊層內容（亮點、台標層）仍保證在 HUD 之上；`osCss.test.ts` 鎖住圖層順序（疊層 > HUD、工作站；台標層 > 疊層；Radix 浮層 50 > 台標層）、兩個疊層畫布 fixed 滿版且 `pointer-events: none`、`.os-root` 沒有 overflow／clip／contain／transform／filter。驗證者看到實際被切的畫面請附影格，再依影格定位。
  - **磷光拖尾接線**：不透明階段（進入 E3 交接點前、離開 X1／X2）用 `applyTrail`（向 `--page`；CRT 關或第一次＝直接蓋一層不透明 `--page`，不留透明缺口）；透明階段（離開亮點、進入交接點後）用新增的 `applyAlphaTrail`（destination-out）或直接清除。依實際 dt；CRT 關＝沒有拖尾。
  - **減少動態效果**：進入／離開／短轉場本來就不產生轉場狀態（疊層 `kind` 為 null，0 幀）。執行中切換：`useDirector` 偵測到轉場進行中 `instant` 變 true，立刻送 `INPUT(swallowed)` 跳到終點（交接點前後都跳）；疊層元件因 `reduced` 變 true 在同一次 commit 取消繪製（`cancelAnimationFrame`＋清空）；鏡頭與兩側螢幕下一幀直接在終點；輸入閘解除；焦點與宣告走既有的抵達規則。警示閃爍（雷達 `RadarAnimator.frame` 每幀接收 `reduced`，無跨幀狀態）中途切換減少動態效果：下一幀光點常亮、鎖定框常亮加粗、外圈 0.9、ping 環消失，補驗 X2 未測項，已有單元測試。
  - **驗證者 r1 退回後的修正（獨立驗證 r1）**：
    - **進入長幀（>33ms）**：（a）第一次進入點擊後約 17ms 的一幀 66ms——點擊那一幀要做的「第一次」太多：工作站在進入一開始就被「隱藏地」掛上（整頁第一次 render，冷的 JS），加上疊層畫布的 2D 後端第一次配置、雜訊緩衝與字型第一次使用。修法：①工作站掛載改用 `useDeferredValue`（`OsShell`）交給 React 的時間切片，點擊那一幀只做控制室與疊層的事；一旦不再隱藏（交接點、被跳到終點、STATION）一律立刻掛上，不等延後的 render；②控制室待機時（`requestIdleCallback`，沒有的環境 200ms 計時器）在真正的兩個疊層畫布上用和轉場相同的繪製路徑畫 9 個代表幀（進入 4、短轉場 2、離開 3；`painter.ts` 的 `runWarmFrame`／`WARM_FRAMES`），每個閒置回呼只畫一幀，畫完 `stop()` 清空——2D 畫布後端、JIT、字型、台標層都已經熱；預熱不寫驗證掛鉤計數（`silent`）、不排 rAF、減少動態效果時不做、轉場一開始就取消；③雜訊顆粒改成從預先產生的亂數位元組池（畫面像素數 ×2，閒置時一次產生）的隨機起點查顏色表（`fillNoise`），每幀不再逐像素跑亂數產生器。沒有新增任何 render target 或線段。（b）CRT 關時交接點後（約 917ms）偶發的 66ms 幀：交接點那一幀要做整棵工作站子樹的樣式重算（`visibility` 會往下繼承）與繪製記錄。修法：進入 `STATION_PREP_MS`（350ms）後把仍隱藏的工作站「預先畫好」——`data-prep="true"` 時 `visibility: visible`（`opacity: 0` 與 `inert` 不變，看不見也不可互動，`os.css`），重算與繪製記錄在 E1 中段（3D 迴圈輕鬆的一幀）完成；交接點那一幀只剩 `opacity` 與 `inert` 的改變。台標矩形仍在交接點讀一次（此時樣式已是乾淨的，`getBoundingClientRect` 不再觸發重算）。**這些都是依效能推理的保守修法，沒有在瀏覽器量測過；是否達標由下一輪驗證者在有畫面的 Chrome 量。**
    - **減少動態效果在交接點之前切換後焦點在 `<body>`**：跳到終點後套用與一般交接點完全相同的抵達規則（`arrivalOf` 不變），並且在下一幀（`requestAnimationFrame`）檢查——焦點仍在 `<body>`（沒有人移走）才再套用一次（工作站 `main`／控制室選中的頻道按鈕）；焦點已在別處（使用者自己移的）不動。單元測試（jsdom）在這個情境本來就通過，所以真正的原因（瀏覽器在同一個 commit 還沒讓目的地可聚焦，或有人把焦點拿走）無法在 jsdom 重現；補一幀的檢查涵蓋這兩種可能，驗證者請用 r1 的 `focus.mjs` 情境 D 重測。
    - **驗證者 r2 的追加（r2 指出兩個修正沒有生效）**：（A）焦點：r2 診斷在 +150ms 時 `main#main` 仍是 `visibility:hidden`，單次 rAF 重試時 `focus()` 默默失敗。改成有上限的逐幀重試（`FOCUS_RETRY_FRAMES`＝30 幀，約 500ms）：焦點到了目標就停、焦點被移到別的真實元素就停、轉場狀態改變（cleanup）就取消；測試以「`focus()` 在前 N 幀失敗」模擬 hidden→visible。（B）長幀：r2 的 LoAF 顯示這些幀是 render-bound（沒有腳本，是工作站樹第一次樣式／排版／點陣化／繪製），第二次造訪同頻道就乾淨，所以 JS 預熱解不了。追加措施：①預先畫好提早到 `STATION_PREP_MS`＝60ms，並讓第一次排版在隱藏狀態的 E1 完成（rAF 內讀一次 `offsetHeight`，與 commit 分開）；②預先畫好期間 `will-change: opacity`（工作站自己一個合成層，點陣化在交接點之前），`data-prep` 一直維持到進入轉場結束（交接點之後仍在，避免交接點拆掉合成層重畫），STATION 後才移除；`visibility: visible` 的規則仍只在 hidden 時生效。若這樣仍有 first-visit 的長幀，結論是：第一次造訪某頻道頁面的樣式／排版成本在頁面元件本身（大量 DOM／圖表），不改頁面元件就無法再壓低——需要使用者裁示是否放寬到「首次造訪允許一幀長幀」，或另開工作項目處理頁面首次渲染成本。冷的第一次點擊幀同理（baseline X2 也有）。
    - **減少動態效果的直接切換沒有宣告**：沒有轉場狀態時（HUB↔STATION、STATION 換頻道）`OsShell` 的 `cutAnnouncement(before, after)` 回傳開始與完成兩段字串（與有轉場時相同：`進入紀錄`／`回到控制室`／`切換到…`，完成加「已」），先寫開始，`CUT_DONE_DELAY_MS`（150ms）後寫完成，讓讀屏分成兩句；連續操作時舊的完成計時器會被取消。開機結束、沒有變化不宣告。
    - **短轉場最前面幾幀光禿禿的卡片（沒有雜訊與台標）**：原因找到了——rAF 的時間戳是「這一幀開始」的時間，可能比時鐘起點（commit 時的 `performance.now()`）早幾毫秒，`t` 成了負的，`switchNoise(t<0)` 與 `tagRectAt(t<showFrom)` 都回傳「沒有」。繪製器現在把 `t` 夾在 0（`Math.max(0, now - start)`），並且第一幀一律重畫台標層（不信任畫布現有內容）。
    - **磷光殘影在鏡頭推拉時太長**：標準 0.85 在進入 E1／離開 X4 的鏡頭推拉期間會把大字拖出 8–10 份殘影。決定：推拉期間（導演狀態 `entering`／`exiting`）改用較快衰減的 keep——標準 0.55、濃 0.6（`phosphor.ts` 的 `PHOSPHOR_KEEP_MOVING`／`keepForMotion`；`CrtPipeline.render` 多一個 `moving` 參數，`HubCanvas` 的 Pipeline 依 `mode` 傳入）；控制室靜止（含巡視、輕微晃動）仍是標準 0.85／濃 0.88，強度「關」永遠 0。仍依實際 dt 換算，與 fps 無關；標準的 5 幀後殘留 < 6%（約 3–4 幀就看不到）。2D 疊層的拖尾（`trail.ts`）不變。
    - **1280×720 離開時 HUD 列蓋住特寫螢幕下緣（325–425ms）**：未改，留給設計師裁示。這是鏡頭構圖的問題而不是單純的圖層順序（HUD 列在交接點 300ms 就啟用，z-index 本來就高於控制室）：要避開得把特寫的 `lookAt` 往上抬或改變 600ms「螢幕面剛好填滿畫面」的終點，這會連動 `faceRect`（卡片外框接續點 ≤2%）與 camera／faceRect 的既有測試，不是可以順手調的小事。選項：①接受（約 100ms 的下緣被蓋）；②HUD 列在離開 X4 前 125ms 才淡入（不改交接點與輸入閘，只改 HUD 視覺）；③特寫終點留出 HUD 列高度的下緣。
  - **設計師核准的偏離（磷光殘影，鏡頭推拉期間）**：簡報原本要求推拉期間沿用標準 0.85／濃 0.88；設計師核准改用較快衰減的 keep——標準 0.55、濃 0.6（上面「磷光殘影在鏡頭推拉時太長」，`PHOSPHOR_KEEP_MOVING`）。控制室閒置與選取仍是 0.85／0.88。這是對簡報數字的偏離，不是實作疏漏。
  - **驗證者 r4 的修正與結論**：
    - **頻道切換（SWITCH）交接後約 70ms 切換減少動態效果，焦點留在 `<body>`**：有畫面的 Chrome 重現後的真正原因——交接點（抵達 `station`）排好的逐幀重試，被「交接點後幾毫秒狀態又變成 `STATION`」那一次 `useEffect` 的 cleanup 取消了：`arrivalOf(SWITCHING 已交接, STATION)` 是 `null`（本來就不該再抵達一次），原本的寫法把重試綁在 effect 的 cleanup 上，所以剛排好的重試立刻被取消；而交接那一刻 `main#main` 仍是 `visibility:hidden`，第一次 `focus()` 默默失敗，焦點就永遠留在 body。修法：重試迴圈改存在 ref（`focusRetry`），不再綁 cleanup；只有「新的抵達」、「去了與重試目的地無關的狀態」（例如要去 EXITING）、卸載才取消；其他規則（到目標就停、被使用者移到別的真實元素就停、上限 `FOCUS_RETRY_FRAMES`）不變。單元測試用「交接點抵達 station（`focus()` 先失敗）→ 同一幀內被跳到 `STATION`」模擬，舊寫法會失敗。有畫面 Chrome 重測：+70ms 切換 0/40 焦點留在 body（修正前約 1/12）。
    - **第一次進入（整頁剛載入）一幀 66–83ms：定位為「第一次排版時的文字塑形與字型初始化」，未能壓到 ≤ 33ms，沒有併入程式碼（等待設計師／使用者裁示）**。Chrome 追蹤（硬體加速，AMD Radeon 780M）：點擊後約 40ms 的那一幀，主執行緒 BeginMainFrame 共 70ms，全是「整份文件的樣式重算 7ms ＋ 排版 61ms」，沒有任何腳本；排版裡 `InlineNode::ShapeTextIncludingFirstLine` 四次各 8–12ms（共約 40ms）。LoAF 顯示該幀的腳本只有 React 時間切片的 5ms 小段，渲染段約 70ms。工作站此時只有 255 個元素（紀錄頁、5 筆範例資料），但中文用 Noto Sans TC 的 unicode-range 切片字型，第一次用到某個切片的字形才建立 HarfBuzz face 與字形快取，並且走備援字型查找；`document.fonts.load` 只把檔案載進來，不會塑形，所以第一次造訪某頁要一次付清，第二次就乾淨。實驗：（1）在控制室閒置時用「與工作站頁面完全相同的文字」預先排版一次，第一次進入的那一幀降到 ≤ 33ms（但那段預熱本身要連續 300ms 以上，且文字需事先知道，只是上限驗證）；（2）改成可上線的版本——紀錄資料的字＋整個 `web/src` 非 ASCII 字池（約 1,058 字，含 → ◀ ▮ 這類備援符號），在閒置回呼裡分塊（每回呼 ≤ 4–6ms）用螢幕外 `visibility:hidden` 容器排版，字型優先排序、含等寬疊層——點擊那一幀由 70ms（rAF 間隔 +70）降到約 52ms（+35），約三到五成的載入完全乾淨，但不穩定，而且仍有 > 33ms（剩下約 35ms 的樣式＋排版，其中第一次整份 454 個 dirty 物件的排版約 25ms 與字型無關）；預熱本身在控制室閒置時偶爾多一幀約 35ms。結論：字型預熱只能把一幀砍掉約一半，達不到 ≤ 33ms，不值得為它多一份字池與閒置工作而不合入。剩下的是頁面第一次進入時樣式＋排版的實際成本，要再壓低只有三條路：①接受「整頁載入後第一次進入允許一幀約 50ms」；②改頁面元件（讓頁面首繪更便宜／分批），違反「不改頁面元件」；③在控制室閒置時真的把選中頻道的頁面在螢幕外 render 一次（需要把路由與資料查詢也預熱，副作用與記憶體風險大，不建議）。另有一個只出現在「瀏覽器開啟後第一個載入」的交接點（約 920–1000ms）53–71ms 幀，是整個瀏覽器第一次的 GPU 點陣化／著色器，不是這個工作站的內容，之後的載入都沒有。
    - **設計師裁示（r4）**：①第一次進入（整頁剛載入）後點擊 1–2 幀有一幀約 50–80ms（第一次中文字塑形加上剛掛載工作站的第一次完整排版；main 上本來就有 52–70ms；之後的進入 0 幀 > 33ms，離開沒有）：**核可為已知偏離**，要修需改頁面元件或離屏預先渲染頁面，留到 X5。②1280×720 離開 325–425ms 時 HUD 列輕觸特寫螢幕下緣（沒有切到字）：**接受**，記為次要備註。③P6（進出 20 次 heap）在驗證腳本下 +10.9%，與 main 同腳本 +10.3% 接近：以並排量測（r5）裁定，與 main 差 ≤ 約 1 個百分點視為既有量測雜訊。
  - **驗證掛鉤**：網址 `?osdebug=transition`（可與其他旗標以逗號並列）時，`window.__osTransition()` 回傳目前（或最近一段）轉場的快照：`kind`、`tMs`、`overlayFrames`（疊層實際繪製的幀數；減少動態效果必須是 0）、`overlayFrameTimes`、`hubFrameTimes`（進出轉場期間 3D 迴圈每幀間隔，驗收「沒有任何一幀 > 33ms」）、`faceRect`（螢幕面目前的投影矩形，視窗比例）、`cardFrame`（疊層卡片外框，視窗比例）、`tagTarget`（交接點讀到的真實台標矩形，CSS 像素）、`tagRect`（疊層台標目前矩形）、`camera`（位置、看向點、進度）、`cleanTail`。沒有旗標時所有掛鉤第一行就返回，不配置物件。

## 11. 風險與回退

| 風險 | 對策 |
|---|---|
| 使用者電腦的顯示卡跑不動 | 低解析度繪製＋線段上限；P1 的降級順序；X0 先在使用者電腦上量測 |

| 3D 套件讓網頁模式變慢 | `/os` 整棵延遲載入；A5、P4 檢查 |
| 工作站裡的頁面因外框而版面錯亂 | 外框只加邊距與裝飾，不改頁面內部；S1 與設計審查 |
| 新增功能時忘了加頻道 | 頻道表集中在一個設定檔，測試檢查每個頻道都對應到存在的路由 |
| 完全放棄這個實驗 | 刪除 `features/os/`、`lib/mode.ts`、`os.css`、`/os` 路由、側欄按鈕與兩個套件；網頁模式不受影響 |

## 12. 執行流程與角色

比照 `docs/cyber-theme-spec.md` §12：

| 角色 | 負責 | 執行者 |
|---|---|---|
| 主視覺設計師／顧問 | 這份規格書、每期的設計簡報、設計審查、回答設計疑問、裁定偏離 | 主模型 |
| 工作協調 | 依本文件派發每期工作、串起實作／驗證／修正／文件檢查、開 PR、回報 | Sonnet |
| 實作、驗證、修正、文件檢查 | 同 `refactor-plan.md` §5；驗證依 `.claude/agents/verifier.md` | Sonnet |

**每一期的流程**

1. 設計師寫該期的設計簡報（補充本文件沒寫到的細節），使用者確認後開始。
2. 協調者派發實作：在自己的 git worktree，從最新 `origin/main` 開分支。
3. CI 綠燈後，**獨立驗證者**（不是實作者）依 §9 中該期的驗收條件實測，並提供設計審查用的截圖與影格條。
4. 有問題就修正，再由**新的**驗證者重驗。
5. 設計審查：不符合就退回第 4 步。實作中遇到本文件沒寫到、或寫了但做不到的地方，**先問設計師，不要自行決定**。
6. 文件檢查（`CLAUDE.md`／`AGENTS.md` 同步、`README.md`），並在 §10 標註狀態與 PR。
7. **合併要使用者明確同意**（每個 PR 各自同意）；合併後才開始下一期。
