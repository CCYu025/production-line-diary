# scripts/verify — acceptance tooling (PLD/OS X1)

Zero-dependency Node 22 ESM scripts (Node built-in `WebSocket`/`fetch` + system Chrome over CDP).
Chrome path: `C:/Program Files/Google/Chrome/Application/chrome.exe`, override with `CHROME_PATH`.

## Data safety (read first)

- Never point a server at real data (the `…工作日誌` folder). Only ever use a **fresh copy of `backend/data/example`**.
- Never use ports 3000 / 3001. Convention: **3114 = branch under test, 3115 = baseline (main), 3116 = spare**.
- Always `NO_OPEN_BROWSER=1`. Never run `npm start` / `npm run dev` from the main checkout.
- `serve.mjs` enforces all of this (refuses 3000/3001 and any path containing `工作日誌`) and writes a **marker**
  `<scratch>/serve-<port>.json` (`{port, root, dataDir, …}`, removed on exit). `safety.mjs` uses that marker as proof
  that a port serves a scratch copy; every script that mutates server data (seeding, saving a record, exporting) first checks it
  (`--scratch` must be the same directory you gave `serve.mjs`; default `%TEMP%/pld-verify`).
- Mutations that the scripts do on the scratch data (all idempotent or harmless): `c1` seeds record 4 into the trash and a 1×1 PNG on
  record 3 (identically on both servers, only before `dialog` / `lightbox`); `os-e2e` E5 creates one record (copy of the first record),
  E6 lightbox seeds the same photo. Restart `serve.mjs` for pristine data.

### Export Excel rule (匯出 Excel)

Finding (backend/server.js `app.post("/api/export-xlsx")`): the file is always `path.join(DATA_DIR, "工作日誌.xlsx")`
(`writeSnapshotXlsx(store.records, outPath)` in `backend/lib/xlsx.js`); no request parameter or env var other than `DATA_DIR`
moves it. With `serve.mjs`, `DATA_DIR` is the scratch copy, so the export stays inside it. **Before any script clicks 匯出 Excel it must call
`exportTargetInScratch(url, scratch)` from `safety.mjs`** (static check of the served root's `server.js` + marker; nothing is exported by the check). It
returns `{ok, outPath, evidence}`; if `ok` is false (route changed, `DATA_DIR` not inside scratch, no marker) **skip the click and say so**.
`os-e2e --only e1` does exactly that. A human verifier must do the same: only export against a `serve.mjs` server and
confirm the toast path points into the scratch folder.

## Starting servers

Build first (`npm run build` in each worktree → `web/dist`), then (run in the background):

```
node scripts/verify/serve.mjs --root <branch worktree> --port 3114 --scratch <scratch dir>
node scripts/verify/serve.mjs --root <main worktree>   --port 3115 --scratch <scratch dir>
```

Flags: `--root` worktree, `--port`, `--data-from` (default `backend/data/example`, relative to root), `--scratch`
(default `%TEMP%/pld-verify`). It copies the example data to `<scratch>/data-<port>-XXXX`, spawns `node backend/server.js` with
`DATA_DIR`, `PORT`, `NO_OPEN_BROWSER=1`, writes the marker, prints the URL and runs until killed. Stop it when done (it is a plain
node process listening on the port).

## verify-holo.mjs — `npm run verify:holo` (H2-0)

```
npm run verify:holo -- [--base <main worktree>] [--quick] [--full] [--only a,b] [--out <dir>] [--allow-software] [--diff-base main] [--no-cache] [--no-fail-fast]
```

`--full` additionally runs `os-handoff-4x` (the same os-handoff at CPU 4x, more than 25 minutes). **Use `--full`** for: every L2 round of H2-5, the last L2 round of every phase from H3 on, and any PR that touches the input gate, the transitions or `useBlocker`. Without `--full` that item is `N/A` (not counted in the totals, does not make the run INCOMPLETE).

**Known-on-main rule (4x only, designer ruling 2026-11-17).** At CPU 4x the I2 post-handoff samples sometimes fail with a phase timeout (`timeout waiting for phase …-post (have …-pre>…)`), and main shows the same thing. So in `os-handoff-4x`: if **every** FAIL sample is an I2 phase timeout that matches the single allowlist entry `osHandoff4x.knownOnMain` (id `I2`, kind `phase-timeout`: every note matches the pattern that `known-on-main.mjs` `phaseTimeoutPattern()` builds from the phase names in `os-phases.mjs`, i.e. only the three real `<kind>-post` phases, each paired with its own `<kind>-pre` first in the `have` list, and only real phase names after it; any other phase name, a mismatched pair or trailing text does not match. `os-phases.mjs` is also what `os-handoff.mjs` builds its scenario table from, and `os-phases.selftest.mjs` fails if it ever differs from the `Phase` type in `web/src/features/os/director/reducer.ts`), and `--base` was given, the same verify run re-measures I2 on the `--base` worktree (3115, `os-handoff.mjs --throttles 4 --only i2 --reps <knownOnMainReps>`, 15 reps = 45 offset-0 samples, roughly 10-15 minutes). If main shows at least one phase timeout too, the item is **INVALID** (value has `knownOnMain: true` plus the base evidence; exit 2; goes to L2/designer, never a pass). If main shows none, or `--base` was not given, or the `--base` server cannot be started or its build fails (message: "the base (main) side could not be started: ... a problem on the base side, so it cannot be compared with main"), it is a plain **FAIL**. Any other FAIL (a leaked click, swallowed input, a non-I2 sample, an I2 sample whose message is not a phase timeout, a sample with an extra note) is a plain FAIL with no comparison. The 1x `os-handoff` item never uses this rule.

**Ratio rule (designer ruling 2026-11-17, replaces "at least one main timeout is enough").** INVALID needs both: (1) main timed out at least once in the same run, and (2) `branchTimeouts <= 3 x baseTimeouts x (branchSamples / baseSamples) + 2`, samples being I2 samples (branch: the I2 rows of the 4x run; base: the I2 rows of the re-run). Otherwise FAIL. A fixed threshold does not depend on the sample count; the ratio answers whether this is a pre-existing property of main at that rate. `value` has `branchTimeouts`, `branchSamples`, `baseTimeouts`, `baseSamples`, `limit`. If the base re-run itself fails (no usable `result.json`, or an exit code other than 0/1) the item is a FAIL whose message says "base re-run failed ... cannot be compared with main" with the exit code and log path. The decision is a pure function (`knownOnMainDecision()`, `ratioVerdict()`, `judgeBaseRerun()`), checked by `known-on-main.selftest.mjs` (18/18 vs 1/60 FAIL, 2/18 vs 1/60 INVALID, 3/18 vs 1/60 FAIL, base 0 FAIL, base re-run failed FAIL).

**Suspend detection (wall clock).** Windows Modern Standby freezes node and Chrome together, and a frozen item used to look like an ordinary timeout. `verify-holo` records a `Date.now()` heartbeat every 5 s; a gap **strictly longer than 60 s** between two heartbeats means the process was suspended (exactly 60 s does not count). Every **time-sensitive** item whose run overlaps a gap becomes **INVALID** with the reason `system suspended (gap Ns at HH:MM:SS), rerun required`, whatever its own verdict was (this beats the timeout verdict); `value.suspendedGaps` lists each gap's start clock and seconds, and the item's original verdict stays in `value.originalStatus` / `originalReason` next to its own evidence, so a FAIL's evidence is not lost. A FAIL that did not overlap a gap is never changed. **Whitelist:** only items flagged `T` in `ITEM_DEFS` (`verify-holo.mjs`) are reclassified: `c1-web`, `c1-os`, `os-e2e`, `os-handoff`, `os-handoff-4x`, `holo-ime`, `holo-still`, `holo-perf`, `holo-perf-20k` (browser, input timing, frame rate). The static items (`ci-check`, `ci-test`, `ci-typecheck`, `ci-test-web`, `ci-build`, `ci-bundle`, `entry-delta-vs-base`, `tests-untouched`, `redline-grep`, `lab-bundle`: build, tests, sizes, diff scans, whose result does not depend on the clock even when slow) keep their verdict (a FAIL stays a FAIL, exit 1; the gap is still in the top-level `suspendedGaps`). A new item is static unless it is flagged. The top-level JSON has `suspended: true` and `suspendedGaps`, and the last stdout line ends with `SUSPENDED Nx (...): rerun required`. **L1: when you see a suspended INVALID, report "environment suspended, rerun needed", not a product result.** The tool never prevents sleep and never touches power settings; that is the user's decision. Pure logic in `suspend.mjs` (`findGaps`, `classifySuspend`, `applySuspend`, `applyTimeout`), checked without a server by `node scripts/verify/suspend.selftest.mjs`.

**Stale result files, the 40 minute timer, exit codes (L2-i fixes).** (1) Before every child process that is supposed to write a result file (`os-handoff` branch and base re-run, `os-e2e`, `c1`, `holo-ime`, `holo-still`, `holo-perf`, the bundle jsons), `verify-holo` deletes the file an earlier run left in the same `--out`: a child that crashes without writing can never be judged on the previous run's numbers (a crashed base re-run is a FAIL "base re-run failed", a crashed branch run is INVALID "no result.json"). (2) A command killed by the 40 minute timer: if the item already shows a FAIL, the FAIL stays (the reason says a command hit the timeout and was aborted); otherwise the item is INVALID with `aborted on timeout`. (3) `os-handoff` exit code and its own summary must agree (without `--allow-deviated`: exit 0 = no FAIL and no DEVIATED, 1 = FAIL, 3 = DEVIATED only; **with `--allow-deviated`, which `holo-baseline.json` always passes, DEVIATED only is exit 0 and exit 3 is a contradiction**; exit 2 is the usage error; the flag is read from the args built by `buildHandoffArgs()`, the single place that builds the command line for the real run and the self-test): any contradiction is `internal error: ...` = FAIL (`handoffExitProblem()`). Checked end to end, with the real `verify-holo.mjs` and a fake os-handoff, no browser and no port, by `node scripts/verify/verify-holo.selftest.mjs` (it sets `VERIFY_HOLO_SELFTEST=1`, which stubs the build and the servers, swaps the os-handoff script and shortens the timer; the hooks do nothing without that variable). **Hard conditions of that hook:** (1) only the exact string `1` enables it; `true`, `0`, empty, ` 1` are ignored with a stderr warning; (2) with `CI` set (non-empty) it is refused: no item runs, last line `VERIFY:HOLO FAIL ... refused ...`, exit 1 (the self-test removes `CI` from its child environment, so it still runs on GitHub Actions); (3) while it is enabled the result is never PASS and the exit code is never 0: the last line is `VERIFY:HOLO SELFTEST ...`, `verify-holo.json` has `"selftest": true`, exit is 2 (1 if an item FAILs, still non-zero). **Exit code as a pure function:** `exit-code.mjs` `overallExit({fail, skip, invalid, selftest, incomplete})` (1 any FAIL; 2 no FAIL but a SKIP / INVALID / interrupted run / hooks on; 0 otherwise); `verify-holo.mjs` calls nothing else, and `exit-code.selftest.mjs` pins the table, including "hooks on and all PASS -> 2, never 0". **Every item that needs `--base` (main) treats a base side that cannot be started or built as FAIL (exit 1), never INVALID** ("the base (main) side could not be started ... cannot be compared with main"): `c1-web` and `c1-os` (base server: no `backend/server.js`, base build failed, port busy, serve.mjs died), `entry-delta-vs-base` (base build failed, no entry measurement for base), and the known-on-main re-run of `os-handoff` / `os-handoff-4x` (`baseUnavailableDecision`). Without `--base` those items are still SKIP (nothing was asked). **The test hooks are a closed list of constants in `verify-holo.mjs`, every one gated by `ST`** (handoff script, holo-ime script, holo-ime url stub, command timeout, base-fail message, fake-pass, baseline file); `node scripts/verify/verify-holo.mjs --dump-hooks` prints their effective values, and `verify-holo.selftest.mjs` (h-1) proves each is inert without `VERIFY_HOLO_SELFTEST=1` (variable unset, `0`, `true`) even with every hook variable set. `VERIFY_HOLO_SELFTEST_FAKEPASS=1` makes every item a fake PASS: the self-test (h-2) uses it to prove that an all-PASS stubbed run still ends in `VERIFY:HOLO SELFTEST`, exit 2, never 0. The scratch folder (`pld-vh-*` in the temp directory) is created only after every early exit, so a refused run leaves nothing there (h-3).
  Self-tests to run after touching any of this: `known-on-main`, `redline-rules`, `suspend`, `os-phases`, `exit-code`, `ime-env`, `base-cache`, `base-guard`, `scrub`, `os-bundle`, `verify-holo` (all `node scripts/verify/<name>.selftest.mjs`, exit 0 = pass). `verify-holo.selftest.mjs` honours `SELFTEST_FILTER=<regex on the case name>` (a developer aid for mutation runs; unset = all cases) and has extra hooks (all inert without `VERIFY_HOLO_SELFTEST=1`): `VERIFY_HOLO_SELFTEST_BUNDLE` (swap the os-bundle script that measures the entry sizes), `VERIFY_HOLO_SELFTEST_FAKESTATUS` (`{"<item id>":"FAIL"}`: that item is a fake with this status, every other item a fake PASS; used to test the stage logic), `--dump-hooks` lists them (including `imeCdpModule`, the effective value of the holo-ime hook below: `null` unless the hook is really honoured). `holo-ime.mjs` additionally honours `HOLO_IME_SELFTEST_CDP=<fake cdp module>` only with `VERIFY_HOLO_SELFTEST` exactly `1` and `CI` empty or unset, so that `ime-env.selftest.mjs` can run the real script's halt wiring without a browser; the rule is one function (`imeCdpModule()` in `ime-env.mjs`) used by `holo-ime.mjs` and by `--dump-hooks`, and `ime-env.selftest.mjs` proves by behaviour (a fake module that records its own import, real child processes with `CI` set, the switch unset, `0`, `true`, ` 1`, …) that the fake is never loaded outside the one allowed combination.

The classification is a pure function (`known-on-main.mjs`, `classifyFails()`), checked without any server by `node scripts/verify/known-on-main.selftest.mjs` (fake `result.json` files: all I2 timeouts, a leak mixed in, I2 but not a timeout, timeout text on an I1 sample, an extra note, no FAIL / empty, inconsistent summary, empty allowlist).

**Two stages, fail-fast (H2-1).** The full version (no `--quick`) runs the quick stage first: groups A and B, in that order. If any item there ended **FAIL or INVALID**, groups C and D are not run: every one of them is `SKIP` with the reason `not run: quick stage failed (<ids>)`, the JSON gets `failFast: {enabled, triggered, by: [ids]}` and the summary line gets `FAIL-FAST: C and D not run because the quick stage failed (<ids>)`. The overall exit code is decided as always (`overallExit`: any FAIL = 1; otherwise the SKIPs make it 2, never 0, so a truncated run can never look like a pass). Only items that really ran count (a SKIP such as `entry-delta-vs-base` without `--base`, or the N/A of `os-handoff-4x`, does not trigger it; `--only` runs the stage logic only over the selected items). `os-handoff-4x` without `--full` stays `N/A` even then. A FAIL inside C does not skip D. `--quick` is unchanged (C and D "skipped by --quick", `failFast.enabled` false). **`--no-fail-fast` runs C and D anyway** (`failFast.enabled` false): use it when L2 needs the complete list of everything that is broken.

**The `--base` cache (H2-1).** The `--base` (main) side is slow and does not change between rounds, so its build and its entry-size measurement are cached by commit. Only the base side: the branch (this worktree) is rebuilt and measured every time, and the known-on-main re-run of `os-handoff` is **not** cached (it decides FAIL vs INVALID and is rare; a stale answer there could excuse a regression). Location: `os.tmpdir()/pld-vh-cache/`, or the absolute path in `VERIFY_HOLO_CACHE_DIR` (refused with exit 2 if it is relative, contains the real-data folder name, or is inside this repo or the `--base` worktree: cache files must never become changes of a tracked tree). One small JSON per key, written atomically (`base-cache.mjs`).
  The key (any difference = no hit, the entry file also stores the whole key and it is compared again): base `git rev-parse HEAD` (full); base worktree **clean** (`git status --porcelain` empty: a dirty or unreadable worktree has no key, so it neither reads nor writes the cache, and the base build is redone every time); sha256 of the base `package-lock.json`; node version; sha256 of `os-bundle.mjs`, `bundle-graph.mjs` and `holo-baseline.json` (the scripts and thresholds that decide the number); the measurement id (`entry-gzip9-static-graph-v1`); **(F1) the build inputs that git does not see**: `nodeModulesHash` = sha256 of the base `node_modules/.package-lock.json` (what `npm install` really put on disk; if that file is missing the installed tree has no identity, so the base is **not cacheable**: nothing read, nothing written, reason `…/.package-lock.json is missing` in `value.baseCache`), and `envHash` = one hash over every `.env` / `.env.*` file directly inside the base `web/` folder (Vite root; `web/vite.config.ts` sets no `envDir`) and inside the base repo root (stricter than Vite needs), where adding, removing, renaming or editing one changes it (an empty file differs from no file), plus the `VITE_*` and `NODE_ENV` variables of the verify run (a build reads them). All of those files are gitignored, so a clean `git status` says nothing about them. What is stored: the sha256 of the base `web/dist` right after the build, the build time, and (after the first measurement) the entry gzip size and when it was measured. **Every hit re-hashes the base `web/dist` that is on disk and compares it with the stored hash**: a dist that was edited, deleted or built from something else is rebuilt (and re-measured), never trusted. Without a hit (or with `--no-cache`, or a dirty base) the base `web/dist` is always rebuilt, even if one exists.
  A corrupt, truncated, wrong-shape, wrong-schema or foreign entry is a miss (rebuild, entry rewritten); an unwritable cache location only means "not cached" (a line in the log). A cache can only make a run faster: the number it returns is the number a fresh measurement of that exact commit and dist gives, and a cached value never turns a FAIL / INVALID into a PASS (the entry-size comparison against the branch is always computed fresh).
  Evidence: `entry-delta-vs-base` in `verify-holo.json` has `value.cached` (true = the base size came from the cache), `value.measuredAt` (when it was really measured), `value.baseCache` (`mode` on / off + reason, `keyDigest`, the key summary with shortened hashes, `buildCached`, `entryCached`), and the log says `base build: CACHED ...` / `base entry size: CACHED N B (measured <time>, key <digest>)`. **`--no-cache` forces a full recompute: nothing is read, nothing is written** (the cache folder is not even created).
  **The `--base` path is never printed in full** in the logs, the JSON or the console: it shows as `…/<last folder>`. (F2) That holds for **every file under `--out`**, not only the item logs: after every item and at the end `verify-holo` sweeps the whole `--out` folder (any extension, nested, except known binary files such as screenshots) and rewrites each file that still contains the path, so the sub-scripts' raw output is covered too (`entry-delta-base.json` `dist`, c1 / os-e2e / os-handoff results). `scrub.mjs` matches every spelling of the separators (`/`, backslash, JSON-escaped doubled backslashes, escaped twice, mixed, doubled) and any letter case, for the path as resolved and as typed; the scrubbed JSON stays valid. Self-tests: `scrub.selftest.mjs` (pure) and `verify-holo.selftest.mjs` `f2-1` (a whole `--out` folder of a run against a base under a folder called `someone`).
  **Threat model of the cache (F3, no HMAC on purpose).** The cache folder is writable by the same user that runs `verify-holo`, so any other process of that user can write a forged entry. An HMAC key would have to live in a place that same user can read, so it would stop nothing; it is not used. What is and is not checked on a hit: (1) the key digest and the whole key summary stored in the entry must equal the key computed now; (2) the base `web/dist` on disk is **re-hashed** and must equal the stored `distHash`, so a hit can never be paired with a dist other than the one the entry names; (3) the stored `entryGzip` is **NOT re-measured** against the dist on a hit, it is taken from the entry (re-measuring is exactly the cost the cache removes). So an attacker (or a bug) that can write the cache folder can write an entry with the current dist hash and any `entryGzip`, and that number would be used for `entry-delta-vs-base`. **When that risk must be excluded (end-of-phase L1, anything that decides a merge), run with `--no-cache`**: nothing is read from or written to the cache, the base is rebuilt and re-measured. Not reachable from the branch side: the branch is never cached.
  **Base guard (`base-guard.mjs`, designer ruling: a whitelist, no parsing).** `--base` must be a **linked worktree** (like `pld-wt/h2-base`) and must contain **no `.env*` entry at all**. Why: the base is a worktree we create ourselves and `serve.mjs` sets `DATA_DIR` for it (a scratch copy of the example data), so it never needs a `.env`; the main checkout has a `.env` that points at the real data. Judging what is *inside* an `.env` (dotenv and node parsing quirks, line breaks, case-insensitive file systems, links) turned out to be a way to be fooled, so file content is **never read or parsed**. Before anything of the base is read (the cache key, the cache), built or served, `verify-holo` refuses when: (1) `git rev-parse --git-dir` and `--git-common-dir` of the base resolve (realpath) to the same folder (a main checkout, also when reached through a junction or link), or the base is not a readable git worktree (fail closed); (2) **any `GIT_DIR`, `GIT_COMMON_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` is set** in the environment (git would answer for another repository; the message names the variable, never its value), and the guard's own git calls run with those variables removed; (3) anywhere in the base worktree (recursive) there is an entry whose name is `.env` or `.env.*` **in any letter case**, whatever it is (file, directory, symlink, junction, broken link); the name is checked three ways: the entry's own name, the name its realpath ends in, and (for a link) the name its target ends in. The **only exception** is a template file `.env.example`, `.env.sample` or `.env.template` (any case) that is a plain file, **tracked by git, and identical to HEAD** (`git ls-files --error-unmatch`, then `git hash-object` against `git rev-parse HEAD:<path>`); an edited (staged or not), untracked, removed-from-the-index, new-in-another-folder template, or a template replaced by a link, is refused like any other. Not scanned (never loaded by the app or Vite, or build output): `.git`, `<base>/node_modules`, `<base>/web/node_modules`, `<base>/web/dist` (the real `pld-wt/h2-base` has no `.env*` entry in any of them, and its only `.env*` is the tracked `.env.example`). A refusal makes **every item that needs the base** (`entry-delta-vs-base`, `c1-web`, `c1-os`, and the known-on-main re-run of `os-handoff-4x`) a **FAIL** (not SKIP, not INVALID; exit 1) with a message such as `base guard: --base contains web/.env.local (an .env* entry that is not an untouched, tracked template); a base worktree needs no .env, remove it` (at most three relative paths are named, never any content); the cache folder is not touched. **Messages, logs and JSON never contain `.env` content**: the cache key only stores a hash of the `.env*` files (kept as a second layer), and `verify-holo.selftest.mjs` (bg-4) scans the cache folder, the whole `--out` and stdout / stderr for a planted unique string. Self-tests: `base-guard.selftest.mjs` (pure) and `verify-holo.selftest.mjs` bg-1 to bg-5 (a temp main checkout plus a linked worktree; bg-5 = several base items in one run and the `GIT_*` variables). File symlinks need a privilege Windows may not grant, so those cases print `(skip)`; junction cases (including a junction named `.env`) always run. Remove an unwanted `.env` from the base worktree by hand; the tool never deletes one.

## os-handoff.mjs — I1–I4

```
node scripts/verify/os-handoff.mjs --url http://localhost:3114/ [--throttles 1,4] [--only i1,key,switch,i2,i3,i4] [--kinds enter,exit,switch] [--reps 3]
   [--viewport 1440x900] [--osdebug a,b] [--enter-step 50 --exit-step 50 --switch-step 25] [--tolerance 25] [--attempts 3] [--strict-focus] [--allow-deviated] [--headed] [--out dir]
```

- Hook (`os-common.mjs HOOK_SRC`): stamps every `data-os-phase` change and every pointer/key event with `performance.now()`. The click/key is **armed before the
  transition is triggered** (`__at(phase, since, offset, lead)`), so it is issued at *phase-change stamp + offset*; the **achieved** offset is then computed from the stamps.
  A sample whose achieved offset differs from the planned one by more than `--tolerance` (25 ms) or that lands in another phase is **DEVIATED**: retried (CDP latency compensation is learned),
  and if it never lands it is reported as DEVIATED – inconclusive, never counted as a pass. A behavioural failure at any achieved offset inside the pre phase is a FAIL.
- Exit code: 1 any FAIL; 3 no FAIL but DEVIATED samples; 0 clean (`--allow-deviated` turns 3 into 0).
- **Precision caveat**: software GL (headless default, SwiftShader) saturates the renderer main thread right after a transition starts, so early offsets (≤ ~150 ms) are often not reachable (many DEVIATED).
  For authoritative numbers use `--headed` on a GPU machine (as for P1); for a headless smoke use `--viewport 1024x640 --osdebug nobloom,nosway`. Hub canvas load is the dominant factor.
- I1 pointer: ENTER 0..850 step 50 × {over `/records` sort control, over HUD CH-02}; EXIT 0..**300** step 50 × over HUD CH-02 (pre-handoff window; the 300..900 ms remainder is covered by I2 below); SWITCH (CH-02→CH-01, via `location.hash` and via palette `dash`) 0..75 step 25 × {over ◀ HUB, over a dashboard KPI card}.
  Asserts: phase jumps to `station`/`hub`, hash unchanged (no `sort=asc`, no navigation), no dialog, underlying control not focused, no phase regression after the jump (stale timers), then the second click on the real target works.
- I1 keyboard (`--only key`): Enter and Space at several offsets, **focus placed on a real control** (enter: another HUD button / EXIT; exit: the sort control; switch: ◀ HUB). The control must not act; the keydown target and focus
  placement are printed. If every candidate is inert the focus falls to `body` (noted; `--strict-focus` turns that into a FAIL).
- I2: first click 0/10/25/50 ms after the `*-post` stamp (enter/switch) must hit the destination target (pointerdown target label checked, then the effect: `sort=asc` / `entering-pre` / `exiting-pre`).
  **EXIT is sampled further: 0/10/25/50/100/200/300/400/500/600 ms after `exiting-post`, i.e. 300..900 ms after the transition start** (X5 §5.1: the whole 900 ms is covered; the last offset may land in the `hub` end phase, which is accepted because input must be live there too). None of these clicks may be swallowed.
- I3: 12×7 grid + corners + centre sampled every frame/16 ms over palette open/close, enter, short switch and exit: overlay computed `pointer-events:none` in every phase, never returned by `elementFromPoint`, all 8 phases seen (missing ones listed).
- I4: hub → 10 × (Enter/click on HUD CH-02, 100 ms, Esc, 100 ms) + a final enter (keyboard and pointer variants). After settling: exactly one stable `data-os-phase` token, route ⇔ phase (`#/os` ⇔ hub), no `#os-overlay[data-active=true]`, overlay `display:none`, one live region,
  no dialog, focus on a HUD button (hub) or inside `#main` (station), state unchanged 600 ms later.
- Writes `<out>/result.json` (every sample with planned/achieved offset), prints a matrix.

## The H1 lab scripts (need the LAB build: `VITE_HOLO_LAB=1 npm run build`)

```
node scripts/verify/holo-ime.mjs   --url http://localhost:3114/ [--methods proj,css3d] [--freeze 1,0] [--out dir]

```

- All four launch **headed** Chrome (`cdp.mjs`) and write nothing to the app data. `holo-perf` and `holo-still` stop with `INVALID` (exit 2) when the WebGL renderer is SwiftShader / llvmpipe / software.
- `holo-ime` (HF3, automated half): for each positioning method × freeze setting, drives the slate while the (script-driven) world moves: the spiral does not turn by itself, so the script drifts the yaw and flips the cursor one day back and forth, which moves the slate anchor: composition then Enter (plain and IME-style key 229), ArrowDown/Up, Escape in the `<input>`,
  the `<textarea>` and the `Combobox`; checks no dropped text, no newline / option / submit during composition, and that Enter outside composition does submit. Key events during CDP composition are sent as keydown+keyup only
  (no char event), like a real IME. **Not measurable here: where the OS candidate window appears** - that is the manual Zhuyin session.
  **Known E2E limit:** CDP key events during a composition always carry `isComposing: true`, so removing only the `keyCode === 229` half of the guard in `Combobox.tsx` / `CopyPicker.tsx` is invisible to this script. That branch (Android-style keyboards: keyCode 229, `isComposing` false) is owned by the unit test `web/src/components/imeKeyCode229.test.tsx` (Enter, ArrowDown, ArrowUp, Escape, both components).
  Gate self-check: `node scripts/verify/holo-ime.mjs --url … --kill-probe` (or env `HOLO_IME_KILL_PROBE=1`, also through `verify:holo`) skips the probe composition; the result must be INVALID (exit 2), never FAIL, never PASS. The switch exists in this script only.
  **Environmental exceptions (H2-0, designer ruling 2026-11-17).** The kinds that count as "the environment, not the product" are one constant, `ENV_ERROR_KINDS` in `ime-env.mjs`: `page-not-ready` (the lab page never got `window.__holoLab().frames > 10` / `__holoLab` missing, only before the first check), `cdp-connection-lost` (CDP timeout / socket closed), `target-closed`. `holo-ime.mjs` turns such an exception into exit 2 with `envError {kind, step, message}` in `result.json` (step = method, freeze and phase, e.g. `proj freeze=0 page-ready`) **only if every check before it passed**; any other exception, or one after a failed check, is a FAIL check ("harness exception ..."). Examples of what stays FAIL: `Execution context was destroyed` (could be the product reloading), an unlisted error.
  **Anti-masking: one in-place retry, done in `verify-holo.mjs` (not inside holo-ime.mjs), because the verdict is made there and the first attempt's file is kept as `result.attempt1.json`.** On an environmental exception `verify-holo` runs holo-ime once more: retry ends in the SAME kind -> FAIL ("two consecutive ..., possibly the product's render loop did not start"); retry PASS -> **still INVALID** (a retry never washes the first exception out); retry with a real failed check -> FAIL; retry INVALID by another kind or the probe -> INVALID. The item's JSON `value` records `retried: true`, `firstAttempt {kind, step, message}` and the retry's summary, and the one-line summary / `reason` always contains "retried 1x". Pure logic and its self-test: `node scripts/verify/ime-env.selftest.mjs`; the retry end-to-end (fake holo-ime, no browser): `verify-holo.selftest.mjs` cases ime-1..ime-6.
  **Who guards the real command line.** `verify:holo` always runs holo-ime with **`--methods proj --freeze 1,0`** (plus `--url` and `--out`): the arguments are one constant, `HOLO_IME_ARGS` / `buildImeArgs()` in `ime-env.mjs`, used by both the real run (first attempt and retry) and the self-test. `ime-env.selftest.mjs` pins the constant; `verify-holo.selftest.mjs` (h-8) runs the real `verify-holo.mjs` against a fake holo-ime that records its argv and asserts both attempts received exactly that list and that this README sentence is still there; changing the method to `css3d` or the freeze list to `0` fails it. holo-ime's own loop stops after the first exception (`untilHalt()` in `ime-env.mjs`: no further freeze setting runs, so the first exception is the one reported and no extra CDP timeout is waited for).
  **Diagnostics (record only, never judged).** `result.json` has `diag` (short: whether the slate node / the three fields / `window.__holoLab` were swapped, `isConnected`, `visibilityState`, `hasFocus()`, frames at composition start and mid-composition and whether they advanced) always, and `diagFull` (adds the last 80 page events and `longtask` entries from a `PerformanceObserver`) only when a check failed or an exception happened.

## os-p6.mjs — P6 (X5 §5.4 fixed method)

```
# 3114 = branch, 3115 = main/baseline (both started with serve.mjs); headed Chrome on the GPU machine
node scripts/verify/os-p6.mjs --url http://localhost:3114/ --base http://localhost:3115/ [--cycles 20] [--warmup 1] [--rounds 1]
```

- One script, one Chrome launch, both servers measured (separate browser contexts, interleaved; `--rounds N` alternates the order, medians are used).
- **Every heap read is preceded by `HeapProfiler.collectGarbage`** (3 passes) and read with `Runtime.getHeapUsage().usedSize`. Heap baseline = post-GC heap at the hub after
  `--warmup` enter/exit cycles (default 1: the first enter loads the lazy OS chunks, which is not growth); heap after `--cycles` (default 20) further cycles is compared to it.
  Growth vs the cold first hub is printed too (informational).
- Cycle = click the selected HUD channel button, wait `station`, click ◀ HUB, wait `hub` (`--settle` ms pause after each phase).
- **Pass (branch)**: post-GC growth <= `--max-growth` (10 %) **or** <= main's growth + `--max-over-main` (1 percentage point); **and** the WebGL counts from `window.__osGl()`
  (page loaded with `?osdebug=gldebug`) — geometries, textures, renderTargets — are back to (<=) the baseline taken at the hub before the cycles. A missing `__osGl`/counter is a FAIL, not a skip.
  Without `--base` only the absolute 10 % rule applies (printed).
- The WebGL renderer is recorded; software renderer or `--headless` ⇒ `INVALID`, exit 2 (spec §9.4), unless `--allow-software` (then informational, e.g. smoke runs).
- Exit 0 pass / 1 fail / 2 invalid. Results in `<out>/result.json` (all raw heap/GL numbers per round and side).
