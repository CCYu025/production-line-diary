# 產線日誌 — 資料結構說明（資料契約）

> 這份文件的目的：**就算「產線日誌」這個 App 未來停用、重寫、或換一套完全不同的技術，
> 只要這份說明書還在，任何人（或任何新的程式）都能不看 App 原始碼，
> 單純靠這份文件就重新讀懂 `data.json` 裡的每一筆資料。**
>
> 換句話說：資料的「意義」不寫在程式碼裡，寫在這裡。

---

## 資料放在哪裡、各自的角色

實際存放位置由環境變數 `DATA_DIR` 指定（見專案根目錄的 `.env.example`），
內容長這樣（以你目前的資料夾為例）：

```
20260918_工作日誌/            ← DATA_DIR 指向這裡
 ├─ data.json                ← 正式資料庫（唯一的「事實來源」，App 讀寫都是這份）
 ├─ 工作日誌.xlsx              ← 給「人」看的匯出快照（跟最早的原始欄位一致，方便列印/傳給主管）
 └─ 照片/
     ├─ 20260918/            ← 原始照片檔案，日期資料夾名稱 = date 欄位去掉「-」
     │   └─ S__33923103.jpg
     └─ 20260921/
         └─ ...
```

這個 `production-line-diary` 專案（程式碼）跟你的真實資料是**分開**的：程式碼進 GitHub，
真實資料只留在你自己電腦的 `DATA_DIR` 資料夾裡，不會被 commit 進版控
（見專案根目錄 `.gitignore` 裡對 `backend/data/data.json` 的排除規則）。

**三個格式各自獨立、互不綁架：**
- `data.json` 壞了或遺失 → 照片本身還是正常的 `.jpg` 檔案，可以直接用任何看圖軟體打開，只是會失去「哪張照片屬於哪筆紀錄」這層關聯。
- App 停用了 → `data.json` 是純文字 JSON，用記事本、瀏覽器、Excel（Power Query）、Python、任何程式語言都讀得開，不需要裝這個 App。
- 想找別人重做一套更強的工具 → 把 `data.json` + `schema.md` + `照片/` 整包丟給對方，對方不用問你任何問題就能接手。

## 檔案最外層結構

```json
{
  "_meta": {
    "schemaVersion": "1.0",
    "exportedAt": "2026-09-22T09:00:00+08:00",
    "app": "產線日誌"
  },
  "records": [ /* 見下方欄位說明 */ ]
}
```

`schemaVersion` 是給「未來的自己或別人」看的版本號。以後如果欄位有調整（例如新增一個欄位），版本號會跟著往上加一版，讀取程式應該要能容忍「舊資料沒有新欄位」這件事，而不是直接壞掉——這是保持資料能長期累積、不用每次改版就要搬家重建的關鍵設計。

## `records` 陣列：每筆紀錄的欄位

| 欄位 | 型別 | 必填 | 允許值 / 規則 | 說明 |
|---|---|---|---|---|
| `id` | 數字 | 是 | 新增時遞增的流水號 | 這筆紀錄的唯一識別碼 |
| `date` | 字串 `YYYY-MM-DD` | 是 | 例：`2026-09-21` | 事件發生日期。對應照片資料夾 `照片/<date 去掉"-">/`，例如 `2026-09-21` → `照片/20260921/` |
| `shift` | 字串 | 是 | `早` / `中` / `晚` | 班別 |
| `time` | 字串 `HH:MM` | 是 | 24 小時制，例：`14:00` | 事件發生時間 |
| `duration` | 數字（分鐘） | 是 | 正整數 | 停機/處理耗時 |
| `equipment` | 字串 | 是 | 自由文字（例：原材區1/原材區2/F3/F4/F7/RB2…），**不是固定清單** | 設備／區域。前端下拉選單的建議清單是即時從現有資料算出來的（`knownEquipment()`），不是寫死在程式碼裡的 enum——因為現場一直會冒出新代號（例如 RB2 就是後來才出現的），寫死清單只會一直落後現實 |
| `category` | 字串 | 是 | 自由文字（例：取料異常/缺料/尺寸異常/沾模/材料損傷/設備異常/其他），**不是固定清單** | 問題的分類，供統計彙總用；跟 `equipment` 同理，前端建議清單是動態算出來的。`category` 是「代碼化」過的類別，`problem` 是完整文字描述，兩者都留著才能兼顧統計準確度與現場細節 |
| `problem` | 字串 | 是 | 自由文字 | 問題的完整描述 |
| `severity` | 字串 | 是 | `輕微` / `一般` / `嚴重` / `重大`（這四個是固定的，見下方理由） | 嚴重度。**衍生規則**：新增時依耗時自動建議——`≤10分`＝輕微、`11–15分`＝一般、`16–20分`＝嚴重、`>20分`＝重大；使用者可手動覆蓋。存進 `data.json` 的是「當時決定的最終值」，不是即時計算值，所以就算未來規則改了，舊資料的意義不會跟著變動 |
| `action` | 字串 | 選填 | 空字串代表未填寫 | 現場處理方式 |
| `rootCause` | 字串 或 `null` | 選填 | `null` = 尚未填寫 | 根本原因（5W1H 裡的 Why） |
| `status` | 字串 | 是 | `待處理` / `追蹤中` / `已解決`（固定），預設 `待處理` | 處理狀態 |
| `photos` | 字串陣列 | 是（可為空陣列 `[]`） | 陣列裡每個字串是照片檔名 | 對應到 `照片/<date 去掉"-">/<檔名>` 這個實際檔案路徑，本身不存放照片內容，只存檔名 |
| `updatedAt` | 字串（ISO 8601 時間戳）或 `null` | 選填 | `null` = 從未編輯過 | 最後一次編輯的時間 |
| `deleted` | 布林值 | 是 | `true` / `false` | 是否已軟刪除（移到回收桶，資料仍保留在檔案裡） |
| `deletedAt` | 字串（ISO 8601）或 `null` | 選填 | `null` = 未刪除 | 刪除時間 |

**為什麼 `equipment` / `category` 是開放式，`severity` / `status` 卻是固定的？**
因為前兩者描述的是「現場實際發生了什麼」，種類會隨產線狀況持續變多；後兩者是「App 自己定義的管理維度」（嚴重度分級、處理進度），這是設計上刻意固定的分類邏輯，不該因為某天多了一種設備就跟著變動。

## 關於 `工作日誌.xlsx`

這份 Excel **不是**即時資料庫，是「匯出快照」——欄位跟你最早的原始表格一致（日期/班別/時間/耗時/設備/問題/處理/照片），方便你照舊打開、列印、傳給主管看。完整資料（分類、嚴重度、根本原因、狀態、是否刪除…）一律以 `data.json` 為準；`.xlsx` 只是給人看的精簡版本，App 不會反過來讀它。

## 給「下一個接手的人／下一套 App」的重點提醒

1. 先讀這份 `schema.md`，不用讀 App 原始碼也能懂資料。
2. `date` 欄位是連結照片資料夾的唯一依據，改資料夾命名規則前要先確認有沒有東西依賴它。
3. `severity` 是「當時決定的值」不是公式即時算出來的，改規則不會動到舊資料。
4. `deleted:true` 的紀錄不要真的刪掉——那是回收桶機制的一部分，除非使用者在 App 裡按「永久刪除」。
5. `equipment` / `category` 不要在程式碼裡改回寫死的 enum——用 `knownEquipment()` / `knownCategories()`（見 `backend/lib/aggregate.js`）從現有資料動態算出建議清單。
